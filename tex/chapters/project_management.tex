\chapter{Gestión del proyecto}\label{ch:gestion_proyecto}

\section{Propósito y enfoque de gestión}\label{sec:proposito-y-enfoque-de-gestion}

El proyecto \textit{Impacto de la calidad del aire en la prevalencia de asma en California}
combina adquisición masiva de datos por API, curación, análisis estadístico/espacial, modelado
predictivo e interpretación de resultados con posibles implicaciones para salud pública.
Este tipo de iniciativas presenta dos retos de gestión típicos: (i) \textbf{heterogeneidad} de fuentes
y formatos (tabular, geoespacial, series temporales), y (ii) \textbf{iteración} inevitable en la
construcción de \emph{pipelines} reproducibles.

Para responder a estos retos, la gestión se apoya en:
\begin{itemize}
    \item \textbf{Estructura de desglose del trabajo (WBS)}: define el alcance mediante fases y paquetes de trabajo.
    \item \textbf{Cronograma (Gantt)}: convierte la WBS en un plan temporal con dependencias e hitos.
    \item \textbf{Control y seguimiento transversal}: mecanismos de coordinación, trazabilidad, calidad y mitigación de riesgos.
\end{itemize}

El enfoque adoptado es \textbf{secuencial por fases}, pero con \textbf{iteración controlada} dentro de cada fase.
En particular, la adquisición y curación de datos se ejecutan de manera incremental (descarga parcial,
almacenamiento intermedio, re-ejecución de procesos) para evitar pérdidas de progreso y para facilitar
la depuración del flujo de trabajo.

\section{Gestión del alcance}\label{sec:gestion-del-alcance}

\subsection{WBS como instrumento de definición del trabajo}\label{subsec:wbs-como-instrumento-de-definicion-del-trabajo}

La WBS organiza el proyecto en fases que recorren el ciclo completo de los datos, desde la
planificación hasta el cierre.
Su objetivo principal es:
\begin{itemize}
    \item \textbf{Delimitar el alcance} (qué se hace y qué queda fuera).
    \item \textbf{Asegurar trazabilidad} entre objetivos, datos, análisis y resultados.
    \item \textbf{Facilitar el control} del avance y la evaluación del rendimiento.
\end{itemize}

\subsection{Entregables y criterios de aceptación}\label{subsec:entregables-y-criterios-de-aceptacion}

Para asegurar una entrega verificable, se definen entregables alineados con las fases principales:

\begin{itemize}
    \item \textbf{E1. Documento de objetivos y requisitos}: objetivos generales/específicos, alcance geográfico/temporal y criterios de calidad.
    \item \textbf{E2. \emph{Pipeline} de adquisición}: scripts para descarga automática, control de versiones de datos brutos y registro de ejecución.
    \item \textbf{E3. Base de datos integrada}: esquema lógico y base de datos que permita consultas conjuntas (calidad del aire + asma).
    \item \textbf{E4. Dataset curado + metadatos}: normalización, control de faltantes, tratamiento de valores atípicos y documentación.
    \item \textbf{E5. Análisis y visualizaciones}: resultados de correlación/tendencias y paneles/gráficas reproducibles.
    \item \textbf{E6. Modelo predictivo}: modelos base y específicos, evaluación comparativa e interpretabilidad.
    \item \textbf{E7. Evaluación de cobertura}: diagnóstico de estaciones/sensores, puntos críticos y deficiencias por contaminante.
    \item \textbf{E8. Publicación y cierre}: informe final, repositorio público con código/datos, y evaluación final del proyecto.
\end{itemize}

Los criterios de aceptación se basan en:
\begin{itemize}
    \item \textbf{Reproducibilidad}: ejecución de scripts/cuadernos con resultados coherentes (mismas entradas $\rightarrow$ mismas salidas).
    \item \textbf{Trazabilidad}: cada figura/tabla relevante vinculada a un procedimiento de generación (script o notebook).
    \item \textbf{Calidad de datos}: reglas explícitas (completitud mínima, coherencia temporal, consistencia geográfica, etc.).
\end{itemize}

\section{Gestión temporal}\label{sec:gestion-temporal}

\subsection{Cronograma mediante diagrama de Gantt}\label{subsec:cronograma-mediante-diagrama-de-gantt}

El cronograma traduce la WBS a tareas calendarizadas, incorporando dependencias y hitos
(\emph{milestones}). Este instrumento permite:
\begin{itemize}
    \item visualizar \textbf{solapes} y \textbf{dependencias} entre fases (p. ej., curación y análisis),
    \item identificar \textbf{camino crítico} (tareas cuya demora desplaza el fin del proyecto),
    \item y programar \textbf{revisiones} de avance orientadas a entregables.
\end{itemize}

\subsection{Hitos y dependencias principales}\label{subsec:hitos-y-dependencias-principales}

A nivel de gestión, se establecen hitos de control que marcan ``puntos de no retorno'' del proyecto:
\begin{itemize}
    \item \textbf{Hito de planificación}: requisitos, KPIs y alcance validados.
    \item \textbf{Hito de \emph{pipeline} de datos}: adquisición y curación automatizadas con almacenamiento estable.
    \item \textbf{Hito de modelado}: modelos evaluados y seleccionados, con interpretación documentada.
    \item \textbf{Hito de publicación}: resultados consolidados, repositorio público y memoria final.
\end{itemize}

Las dependencias clave suelen ser:
\begin{itemize}
    \item La \textbf{curación} depende de una adquisición estable (datos brutos disponibles y versionados).
    \item El \textbf{análisis} depende de la curación (sin reglas de limpieza, los hallazgos no son defendibles).
    \item El \textbf{modelado} depende de la integración (base de datos o dataset final con variables consistentes).
    \item La \textbf{evaluación de cobertura} depende de disponer de estaciones/sensores georreferenciados por condado.
\end{itemize}

\subsection{Herramientas de gestión y colaboración}\label{subsec:herramientas-de-gestion-y-colaboracion}

Para garantizar coordinación y trazabilidad se emplean:
\begin{itemize}
    \item \textbf{Control de versiones}: repositorio para código, documentación y cambios relevantes.
    \item \textbf{Seguimiento de tareas}: incidencias (\emph{issues}), tablero Kanban o lista de hitos por fase.
    \item \textbf{Ejecución reproducible}: cuadernos y scripts versionados con entornos documentados.
    \item \textbf{Almacenamiento}: separación entre datos brutos, intermedios y curados; copias de seguridad.
\end{itemize}

\section{Control, calidad y gestión de cambios}\label{sec:control-calidad-y-gestion-de-cambios}

\subsection{Control y seguimiento}\label{subsec:control-y-seguimiento}

El control se realiza mediante revisiones periódicas centradas en hitos y entregables. En cada revisión:
\begin{itemize}
    \item se verifica el \textbf{estado} de tareas críticas,
    \item se registran \textbf{bloqueos} (técnicos o de datos),
    \item y se acuerdan \textbf{acciones} con responsables y fecha objetivo.
\end{itemize}

Como soporte cuantitativo, se definen KPIs de gestión simples, por ejemplo:
\begin{itemize}
    \item \textbf{Cumplimiento de hitos}: porcentaje de hitos logrados en fecha.
    \item \textbf{Automatización}: proporción de tareas de adquisición/curación ejecutables sin intervención manual.
    \item \textbf{Calidad de datos}: métricas de completitud, consistencia y porcentaje de registros válidos tras curación.
\end{itemize}

\subsection{Gestión de calidad}\label{subsec:gestion-de-calidad}

La calidad se aborda desde dos perspectivas:
\begin{itemize}
    \item \textbf{Calidad de datos}: reglas explícitas (validación de rangos, tratamiento de faltantes, detección de atípicos).
    \item \textbf{Calidad del proceso}: revisión por pares, trazabilidad de cambios y reproducibilidad (misma entrada $\rightarrow$ misma salida).
\end{itemize}

\subsection{Gestión de cambios}\label{subsec:gestion-de-cambios}

Dado que los proyectos de datos evolucionan con el descubrimiento de problemas (p. ej., sesgos,
faltantes, cambios en endpoints), los cambios se gestionan con un flujo sencillo:
\begin{enumerate}
    \item \textbf{Registro}: descripción del cambio y motivación.
    \item \textbf{Impacto}: evaluación del efecto en alcance/tiempo/calidad.
    \item \textbf{Aprobación}: validación por el responsable del proyecto.
    \item \textbf{Implementación}: ejecución y documentación; actualización de scripts y metadatos.
\end{enumerate}

\section{Presupuesto y estimación de esfuerzo (opcional)}\label{sec:presupuesto-y-estimacion-de-esfuerzo-(opcional)}

Si se requiere una estimación económica, puede derivarse del esfuerzo por paquete de trabajo:
\[
C \;=\; H \cdot r \;+\; C_{\mathrm{infra}},
\]
donde $H$ son horas totales estimadas, $r$ una tarifa media por hora, y $C_{\mathrm{infra}}$ recoge
costes de infraestructura (almacenamiento, licencias si aplican, etc.). Para mantener coherencia con
la gestión temporal, es recomendable estimar $H$ por fase/hito (según WBS/Gantt) y revisar la
estimación tras completar los primeros entregables (planificación y \emph{pipeline} inicial).

\section{Cierre del proyecto}\label{sec:cierre-del-proyecto}

El cierre contempla:
\begin{itemize}
    \item \textbf{Verificación de entregables}: informe final, anexos técnicos y repositorio reproducible.
    \item \textbf{Publicación}: datos curados y código con licencia adecuada, y archivado en repositorio de larga duración.
    \item \textbf{Lecciones aprendidas}: incidencias principales, decisiones metodológicas y mejoras para iteraciones futuras.
\end{itemize}

Este conjunto de prácticas asegura que el proyecto no solo concluya con resultados analíticos,
sino también con activos reutilizables (datos, código, documentación) y una base sólida para
extensiones o replicaciones posteriores.
